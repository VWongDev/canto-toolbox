# Testing

## Framework

The project uses [Vitest](https://vitest.dev/) with a standalone config
(`vitest.config.ts`) separate from the Vite extension build, plus
[Playwright](https://playwright.dev/) for end-to-end tests (`e2e/`).

The default Vitest environment is `node`. A global Chrome API mock is installed
for every test via `src/__tests__/setup.ts` (`setupFiles`), so modules with
`chrome.*` side effects can be imported. Tests that need a DOM opt in per-file
with a directive on the first line:

```typescript
// @vitest-environment happy-dom
```

## Running Tests

```sh
pnpm test            # vitest run (single pass, no watch)
pnpm test:coverage   # vitest run --coverage (v8)
pnpm test:e2e        # playwright test (requires a built extension in dist/)
```

CI runs `lint → typecheck → test` (with non-blocking coverage) and a separate
job for `test:e2e`.

## Conventions

- Test files live in a `__tests__/` directory next to their source, named
  `*.test.ts` (e.g. `src/dictionary/__tests__/dictionary.test.ts`).
- Use `describe` blocks grouped by exported function name.
- Assert behavior, not implementation details.

## Mocking Generated Data

The dictionaries are **not** statically imported. `src/dictionary/dictionary.ts`
loads them at runtime by `fetch`ing `chrome.runtime.getURL('data/{mandarin,
cantonese,etymology}.json')` — these JSON files are generated by the build,
packaged from `public/data/`, and gitignored (so they do not exist when tests
run).

Tests therefore stub `globalThis.fetch` and branch on the requested URL, rather
than `vi.mock`-ing a JSON module. See
`src/dictionary/__tests__/dictionary.test.ts` for the canonical pattern:

```typescript
vi.stubGlobal('fetch', vi.fn((url: string) => {
  let data;
  if (url.includes('mandarin')) data = mockMandarin;
  else if (url.includes('cantonese')) data = mockCantonese;
  else if (url.includes('etymology')) data = mockEtymology;
  return Promise.resolve({ json: () => Promise.resolve(data) });
}));
```

Use subsets of real dictionary entries as fixture data — do not invent fake
entries with made-up romanisation or definitions.

## What to Test

**Pure logic** — no browser/Chrome dependency, straightforward to unit test:
- `src/dictionary/dictionary.ts` — lookup, filtering, longest-match
- `src/shared/bounded-map.ts` — map operations, pruning
- `src/shared/debounce.ts` — debounce / batched-debounce timing
- `src/shared/statistics-utils.ts`, `src/shared/redundant-store.ts`,
  `src/shared/storage-manager.ts`, `src/shared/message-manager.ts`

**DOM components** — tested under `// @vitest-environment happy-dom`:
- `src/shared/dom-element.ts`
- `src/shared/pronunciation-section.ts`, `etymology-section.ts`,
  `definition-section.ts`

**Message handlers** — `src/popup/background-handler.ts` is tested with the
dictionary module mocked via `vi.mock('../../dictionary/dictionary.js', …)`.

**End-to-end** — content script ↔ service worker ↔ pages are exercised by the
Playwright specs in `e2e/` (popup, stats, flashcards). The Playwright MCP
server (`.mcp.json`) is available to drive the browser interactively while
debugging.

## Manual Verification

Automated coverage is the primary signal; manual verification is an optional
sanity check for UI-heavy changes:

1. Run `pnpm build`
2. Load the unpacked `dist/` directory in Chrome (`chrome://extensions` →
   Developer mode → Load unpacked)
3. Navigate to a page with Chinese text
4. Hover over Chinese characters — popup should appear with Mandarin and
   Cantonese definitions
5. Open the Stats page via the extension popup to verify statistics tracking

See @.claude/docs/dev-workflow.md for full build and loading instructions.
